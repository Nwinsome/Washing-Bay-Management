# Washing-Bay-Management

An Electron, React and TypeScript desktop application with local SQLite storage.

## Windows development and installer

Use Windows x64 and Node.js 24 or newer (Node 24.17 / Electron 44.7 were used for validation). Run `npm.cmd ci` to install the locked dependencies. Downloads are needed to set up development and packaging; the installed application works offline.

```powershell
npm.cmd run dev
npm.cmd test
npm.cmd run typecheck
npm.cmd run build
npm.cmd run test:desktop
npm.cmd run dist:win
npm.cmd run verify:package
npm.cmd run test:packaged
# Optional: disposable installation QA (writes temporary installation/shortcuts):
powershell.exe -NoProfile -File scripts/test-installation.ps1
```

`dist:win` produces `release/Washing-Bay-Management-System-1.0.0-Setup-x64.exe` and the unpacked application in `release/win-unpacked`. `pack:dir` builds only the unpacked application. The installer supports current-user installation, a chosen installation directory, desktop/Start Menu shortcuts and uninstall. A branded icon and signing certificate have not been supplied; the Electron fallback icon is used and Windows may display an unsigned-publisher warning.

Packaging creates a separate `.desktop-app` directory containing an explicit runtime source list, compiled frontend, SQL schema/catalogue and only runtime SQLite/bcrypt dependencies. The Node-API SQLite binary is checked in the actual Electron runtime before packaging; the Node test installation is not rebuilt. `verify:package` checks the final archive and unpacked native binary for required assets and forbidden databases, test fixtures, secrets and development dependencies. Do not place operational files in the build staging directory.

Run the installer, choose a location and launch **Washing Bay Management System**. On first use enter business information and create your own administrator account; there are no default credentials, prices, salaries or financial balances. Configure category prices and worker compensation before recording work. Existing users should close the application and create a verified backup before installing an update.

The database remains at `%APPDATA%/wash-bay-manager/wash-bay-manager.sqlite`, with external legacy logos in its `logos` subfolder and safety backups in `backups`. The installer product name does not change this historical location. Updates and uninstall preserve this user-data directory. Backups selected elsewhere remain at their chosen destinations. Restrict access to these folders; backups contain password hashes and business records and are not encrypted.

For isolated QA only, `WASH_BAY_USER_DATA_PATH` overrides the complete data directory and `WASH_BAY_DATABASE_PATH` overrides the database file. Desktop tests set both to a temporary directory and remove it afterwards. Never point test settings at operational records. `WASH_BAY_PACKAGED_EXE` can select an installed executable for `test:packaged` without using the real database.

From **Settings and Security**, create a manual backup by selecting a private destination. The result is a `.wbbak` folder; keep the whole folder, including `database.sqlite` and `manifest.json`. Use **Select and verify backup** to check it. Restore requires a validated selection, typed `RESTORE`, the current password, the page confirmation and a final native confirmation. A verified safety backup is mandatory. Restoring replaces operational records and signs out all sessions; use the credentials contained in the restored backup. If recovery is interrupted, preserve the database, safety backups and journal and follow the recovery guidance below.

Troubleshooting: if startup reports a missing renderer or database component, reinstall while retaining user data. In source development, run `npm.cmd ci` and `npm.cmd run build` before `npm.cmd start`. Disk-full, permission and corrupt-database errors must be resolved before retrying; never delete database, WAL/SHM or recovery-journal files to clear an error. Financial dates that are already closed require reopening affected closings latest first. Unconfigured prices/compensation and legacy warnings require explicit administrator decisions, not inferred zero values.

See [Windows acceptance and deployment checks](docs/WINDOWS-ACCEPTANCE.md) for coverage, manual checks and limitations. This build is not declared production-ready solely because automated checks pass.

Installation QA refuses to replace an existing matching installation or shortcut. It temporarily registers a per-user installation and shortcuts, tests first-run/update/uninstall with disposable data, and retains its temporary directory for inspection. Use a disposable Windows account for release acceptance. Dependency audit currently reports no runtime vulnerabilities; eight moderate build-tool advisories remain in the packaging dependency chain, which is excluded from the installed application.

## Setup, login and overview

On first use, complete business setup and create an administrator. Then sign in with that account. Only active administrators can access the overview. Passwords are verified against bcrypt hashes in the main process; no password hashes or session tokens are sent to the renderer. Sessions stay in memory, belong to one Electron window, expire after 30 minutes without a protected API request, and end on sign-out, full navigation, renderer failure or app closure. Five unsuccessful credential checks block further attempts in that window for one minute.

The dashboard reads existing records; it does not create example transactions. It shows work completed today, registered vehicles waiting/in progress, actual completed payments received today, outstanding balances excluding cancelled work, expenses, customers, active workers/services, and the eight most recent transactions. Dates use Africa/Accra (UTC). Cancelling work does not erase previously received payments; refunds are a separate workflow. Legacy visits use their creation date when a completion timestamp was never recorded. Collected payments are not accounting profit. The stored business currency is respected; new setups use GHS.

The services panel configures independent prices. Visit entry is on the **Visits** page. Choose exactly one Washing OR Blowing service for a registered vehicle visit, never both. Carpet cleaning remains independently priced and optional, including standalone carpet cleaning without a vehicle. Workers can wash on one visit and blow on another. Configure compensation on **Worker Earnings** and update the existing administrator account on **Settings and Security**. Additional administrator creation and password recovery are not implemented. There is no default login or password bypass. A business with no usable administrator requires a separately designed recovery workflow; setup is not reset automatically.

## Vehicle categories and flexible service pricing

Application initialization applies `schema.sql` and `catalog.sql` together in a SQLite transaction. The catalogue adds only the 43 vehicle category names supplied by the business and the four vehicle service names: Wash, Blow, Engine Wash and Under Wash. It contains no prices, customers, workers, visits or payments. Existing Washing/Blowing service classifications and recognized Engine/Under Wash services are reused. Existing category names match without case/space differences (including 4×4/4x4). Preset-to-category ID bindings ensure that renaming or deactivating a supplied category does not cause its original name to be recreated on later launches. Existing duplicates are retained for review rather than merged or deleted.

On **Overview**, the **Services, categories and pricing** panel provides a searchable category/service matrix and price editor. Each category/service combination can have an administrator-entered GHS price, be marked **Unavailable**, or explicitly set **Not configured**. A configured GHS 0 is a valid free service. Unavailable and unconfigured entries cannot be charged; changing their status does not delete the prior price row. New vehicle service charges require an explicit price for that category: legacy general vehicle-service prices are preserved but no longer used as automatic fallbacks. Independent services such as carpet cleaning can retain a general price without a vehicle registration. Existing non-GHS business currencies are preserved; new price writes remain blocked until GHS pricing is intentionally configured.

The same panel lets administrators add, rename, deactivate or reactivate categories. Registration and visit category selectors are searchable. Inactive categories are omitted from new registration choices and cannot be used for new visits; vehicles already referencing an inactive category can still have their other details edited. Renaming retains IDs and category-specific prices, while historical visit category names remain in snapshots.

Wash and Blow are alternative main services. Engine Wash and Under Wash are optional vehicle extras that require a vehicle visit with exactly one main service, and are not offered as standalone non-vehicle work. Each chosen main/extra/independent service is stored as a separate line with its own original price and worker assignment and is shown in visit/payment details. Workers can be shared across lines or different workers can perform them. Stable `service_roles` and `transaction_service_roles` metadata extend the existing service classifications without rebuilding or changing historical service/price tables. `service_category_options` stores category availability separately from price amounts. Catalogue migrations never copy prices from photographs or seed default prices.

## Customer visits and payments

Open **Visits** to find an existing vehicle by normalized plate or register a new vehicle with its first visit. New vehicle registration and visit creation commit together or roll back together. Choose exactly one vehicle service, optionally add independently priced services, and assign an active worker to the vehicle service. Carpet cleaning can be recorded without registration and supports an optional worker where applicable. Workers may serve multiple visits; no permanent service role or invented commission is applied. Prices appear automatically in GHS, and saving checks that the reviewed service/worker/compensation details still match current configuration.

Visits start **Waiting** (the existing database status `pending`). Waiting can move to In progress, Completed or Cancelled; In progress can move to Completed or Cancelled. Completed and Cancelled are terminal in this phase. Arrival, start, completion and cancellation times plus an append-only status history are recorded in Ghana/UTC time. Work completion does not require payment and payment does not complete work. Historical names, assignments, prices, configured earnings and vehicle snapshots remain stored values.

The payment form records full or partial amounts actually received, using cash, card, mobile money, bank transfer or other, with date and optional reference. Unpaid visits simply have no received payment. Multiple receipts can be recorded up to the outstanding balance. Amounts are entered in GHS and sent as integer pesewas; `visit_details.total_pesewas` and `payment_receipts.amount_pesewas` are authoritative for new records. Existing REAL amount columns remain intact for compatibility. Legacy balances derive cents from their stored amounts without rewriting them. Pending, failed and refunded legacy payments are not counted as received/credited payments.

Creation and payment submission keys are unique. Retrying the same key/payload returns the existing record; reusing a key for different details fails. Payment writes use immediate SQLite transactions and check the current outstanding balance inside the transaction. Mutation, receipt/metadata and audit records commit atomically. The interface disables duplicate submissions while saving and retains the same payload/key for retry. A new key represents a separate intentional receipt; no unsupported matching or splitting rules are inferred from amount/reference alone.

Cancelled work has no collectible outstanding balance, but existing receipts remain in history and collected totals. Cancellation does not refund money. Refunds, reopening terminal visits, company/customer credit-account terms, shared earnings, taxes/discount entry and shared payroll workflows require separately confirmed rules. Worker service payouts are available in Worker Earnings. There is no existing company credit ledger to extend; the company table alone is not treated as an accounting policy. Existing currency is never changed automatically: this new pricing/payment workflow accepts GHS only; legacy records in another currency remain readable, and conversion needs explicit configuration.

The additive tables `visit_details`, `visit_status_events`, and `payment_receipts` extend the existing `transactions`, `transaction_services`, `transaction_service_workers`, and `payments` records; they do not create duplicate visits. `visit_balances` provides integer totals, paid amounts and outstanding balances. Existing credentials, businesses, vehicles, workers, prices, transactions and payments are untouched by schema reapplication. New records cannot be deleted through this API. The former direct `transactions:create` endpoint rejects requests so it cannot bypass the new lifecycle; transaction reads and pricing quotes remain available for historical compatibility. Old records without tracked events/timestamps are identified as legacy rather than assigned fictional history.

## Workers management

Open **Workers** in the dashboard navigation to register, search, edit, activate or deactivate workers. Registration requires a full name and phone number; email, descriptive job title and hire date are optional. The directory searches name, phone, email and job title, filters by status, and displays 50 workers per page. New workers are active and available to the service assignment picker. Deactivation removes them from new assignment choices while preserving historical visits and payments. Reactivation makes them available again. Editing details does not change the worker ID, status or existing pay rate.

Worker registration uses the existing `workers` table and never creates login accounts or permanent service restrictions. No schema change or migration is needed for this module. Every workers IPC operation checks the trusted application sender and current active administrator session before validating input; SQL values use bound parameters. Mutations and audit entries commit atomically. There is no worker deletion endpoint. Historical assignment names, service prices, rules and earnings remain stored separately from editable worker details. Multiple workers can be assigned across the service lines of one visit (for example, washing and carpet cleaning); washing and blowing remain mutually exclusive on a single vehicle visit.

Compensation configuration, earnings history and service payouts are available in Worker Earnings. Assigning multiple workers to the same service line remains future work. The current service-line model supports one assigned worker per line. Worker-management tests use isolated in-memory fixtures and never seed the real business database.

## Vehicle registration and management

Open **Vehicles** from the sidebar to add, search, edit, archive or activate registered vehicles. Number plate and an existing configurable vehicle category are required; make, model, colour and customer name/phone are optional. The supplied category names are initialized without prices; additional categories can be added from the registration form. The directory searches plates, names and phone numbers, filters by status/type, and displays 50 vehicles per page. Entering a plate checks for returning vehicles automatically and offers their existing record.

New plate displays are uppercase with collapsed spaces. Matching ignores case, spaces and hyphens. New registrations and plate changes are checked by authenticated IPC and SQLite triggers, including matches with archived records: reactivate and reuse those records instead of registering again. Existing legacy vehicles are never merged or automatically archived; ambiguous normalized matches are shown for review. New plates support ASCII letters, digits, spaces and hyphens; existing plate text remains untouched by migration.

The existing `vehicles`, `vehicle_types`, `customers` and `transactions` tables remain intact. Additive `vehicle_record_state` stores archive status and optional vehicle-specific contact details. Legacy contacts come from the existing customer link unless explicitly edited in the Vehicles form. Phone-only contacts do not require a fabricated customer name, and editing contacts does not alter shared customer records or create customer accounts. Registration never creates transactions, payments or fictional customer rows. Archive and activate operations preserve vehicle IDs and all visit links; no vehicle deletion endpoint is exposed.

In the existing visit form, find a registered vehicle by plate and use its recorded type for pricing. New visits can reuse the same active vehicle repeatedly; archived vehicles cannot be selected for new visits. Independent service prices and worker assignments are retained. `transaction_vehicle_snapshots` preserves the plate, type name, details and contact recorded for each linked visit; transaction reads and recent dashboard visits use snapshots. Migration captures the currently available details for older linked visits with `provenance='migration'`; it cannot recover changes made before snapshots existed. Reapplying the schema never replaces these snapshots. Database initialization now applies the schema atomically. Other business and financial records remain untouched.

## Service assignments and compensation model

Each visit has one `transactions` record and separate `transaction_services` lines. `transaction_service_workers` links a worker to an individual line and stores the worker name, compensation method/rate and calculated earnings at recording time. It does not restrict which services a worker may perform. Existing `transaction_workers` visit-level links remain untouched; their service allocation cannot be inferred.

`service_definitions` gives each service a stable classification: washing, blowing, carpet cleaning or other. Recognized existing names (Wash/Washing, Blow/Blowing, Carpet cleaning, ignoring case and outer whitespace) are classified without rewriting business records; custom names can be classified through service configuration. Established classifications remain fixed even after renaming. The interface uses one radio group for washing/blowing, the quote/create API rejects multiple vehicle services, and a SQLite trigger rejects conflicting service lines, including writes outside the API.

New lines snapshot their classification in `transaction_service_details`. Future reports should read `visit_service_records` and the stored assignment/price/earning records, rather than join current service prices or infer services from worker roles. Legacy lines retain their original records and names; the reporting view identifies them with `legacy_record=1` and uses their recorded service names for classification. Old visits containing both washing and blowing remain readable as historical exceptions and must not be merged, split or repriced. New visits cannot record that combination.

The prepared `service_compensation_rules` model supports an explicitly configured fixed amount per service unit or a percentage of that service's line total, rounded to the nearest currency cent. No compensation rules are seeded, and `workers.pay_rate` is not reinterpreted. An assigned service without a rule has NULL compensation and earnings (unconfigured), distinct from an explicit zero rate. The current recording flow uses one unit per selected service. These assignment-time values remain estimates for compatibility; Worker Earnings uses separate immutable completion-time snapshots. Worker payments remain separate from earned amounts. Completed assignment snapshots are read from their stored records, never recalculated from current prices or rules. The schema additions are safe to apply repeatedly and do not reset existing tables or business data.

## Worker earnings and compensation

Open **Worker Earnings** from the sidebar to configure compensation, search workers, filter activity dates, inspect completed-service breakdowns and payment history, and record worker payouts. Activity is paginated in groups of 50. Date filters affect displayed activity totals; payable balances always include all confirmed work and verified payouts. Inactive workers retain their earned balances.

Configure a general fixed GHS amount per service or percentage of that service's recorded charge. Category rules override the general rule; **Use general rule** removes an override and **Unconfigured** explicitly prevents fallback. No rules, rates or amounts are seeded. Fixed amounts use integer pesewas; percentage rates use integer basis points (two decimal places of percent, 0–100%). Percentage earnings round to the nearest pesewa, with half pesewas rounded up, using BigInt arithmetic. Explicit zero rules are valid and distinct from missing rules. The existing general-rule table remains intact; unsupported legacy precision is flagged as unconfigured rather than silently rounded into earnings.

Completion atomically records an immutable snapshot per assigned service line in `worker_service_earnings`, including worker/service/category names, recorded charge, quantity, compensation rule, arrangement and earned pesewas. Pending, in-progress and cancelled work does not accrue earnings. Repeated completion cannot accrue again. Rules and worker arrangements applicable at completion determine confirmed earnings. The original assignment-time estimates remain preserved for compatibility and are labelled as estimates in Visits. New visits also snapshot their category, so later vehicle/category edits cannot change the category used for compensation. Missing rules remain unconfigured, rather than confirmed zero earnings. Customer receipts never determine worker earnings.

Daily and monthly salary agreements accept an explicitly entered amount. Salary work excludes per-service accrual and retains the agreement snapshot separately from service balances. **Automatic salary accrual and salary payouts are unavailable:** the system lacks attendance, payable-day/period, effective-date and proration rules. No salary obligations are generated. Returning to service compensation affects future completions without changing history.

Payouts reuse `worker_payments`, with additive `worker_payout_receipts` for integer pesewas, GHS currency, method, reference and a unique submission key. Immediate transactions commit payment, receipt and audit together and enforce both the current confirmed balance and earnings available by the payment date. Overpayment, future dates and invalid amounts are rejected. Retrying the same key/payload returns the same payout; changing the payload with that key fails. The renderer retains a pending key when a request fails. New keys represent separate intentional payouts; amount/reference alone cannot identify duplicates. Advances, salary payouts and automatic expense posting are unsupported. Worker earnings, worker payouts, customer collections and business expenses remain distinct.

Older completed visits are not recalculated using current rules. Existing estimates and visit-level assignments are preserved. Completed service assignments without a completion ledger are flagged for review and excluded from confirmed earnings. Historical worker payments without verified receipts appear as unclassified amounts with unverified currency. **New payouts for those workers are blocked pending a separately defined reconciliation workflow**, preventing old payments from being misclassified or counted twice. Unknown historical categories require review when category overrides could change compensation. Initialization is additive and idempotent. All earnings IPCs, including reads, require the trusted sender and an active administrator session.

Phase 8 — Expenses and Daily Closing

The Expenses and Daily Closing navigation pages use authenticated main-process IPC. Expense events are integer pesewas, append-only and idempotent. Reversal records retain the original expense and require a reason; corrections are a reversal followed by a replacement expense. Reversals affect their recorded date and original payment method. A reversal must represent an explained bookkeeping correction or actual return of funds; it is not an unpaid expense.

Closing uses service completion dates for charges/services and receipt dates for customer payments, verified worker payouts and expenses. Salary agreements and earned-but-unpaid compensation do not enter cash movement. Outstanding balances are computed using receipts through the selected day for visits created through that day. Legacy service completion dates fall back to transaction creation dates when completion timestamps are unavailable. The saved snapshot includes source IDs, methods, amounts, as-of balances and service charges.

Expected cash = explicit opening cash + cash receipts - cash payouts - net cash expenses. Opening cash has no default: the administrator records an amount (including an explicitly verified zero) and a reason, or uses the previous calendar day's confirmed actual count. Differences require explanations. Negative expected cash is shown rather than silently clamped. No balances or financial sample records are seeded.

Closing revisions and reopening events are immutable. Backdated receipts, payouts, expenses, service completions and charge changes affecting confirmed days are blocked. Reopen affected days latest first, correct the activity, then reconfirm in chronological order. The original snapshots remain available. New payments on later dates do not change earlier snapshots. A review token rejects confirmation when recorded activity changes after review.

Legacy expenses, payouts without verified method/amount receipts and legacy daily_closings are preserved and block closing where their dates affect reconciliation. The UI reports their counts; a supervised legacy reconciliation/import workflow remains to be defined. Dashboard expenses include legacy amounts for continuity, while new daily cash calculations refuse to infer legacy methods.

Business rules still to define: cash float deposits/withdrawals and bankings, customer refunds, salary accrual and actual salary payouts, and historical source reconciliation. The current closing supports recorded customer collections, existing verified service-earnings payouts and paid expense events. Opening cash verification is an administrator attestation; bank account reconciliation and multi-currency operations are outside this phase. There is no new salary payout functionality.

Validation: npm.cmd run typecheck; npm.cmd run build; npm.cmd test. Financial tests use isolated in-memory SQLite databases, not the live business database. Electron visual/manual acceptance should verify the forms and dialogs with real authorized entries before operational use.

Phase 9 — Company Accounts, Credit and Statements

Company Accounts adds company registration, normalized name duplicate prevention, contact editing, search/status filters, activation and explicit administrator credit authorization. New companies have credit disabled with NULL credit limits and terms. Existing companies are preserved; no customer records are merged. Blank limits mean no configured cap, while an explicit zero limit allows no new unpaid charges. Limits cannot be reduced below current outstanding debt. Inactive accounts and accounts with credit disabled cannot acquire unpaid visits; existing debts can still receive payments.

Vehicle assignments are append-only events. New visits inherit the current vehicle company unless an explicit company or Individual Customer selection overrides it. The quote shows the company; save checks the reviewed company identity and credit capacity again. Each company visit stores an immutable company name, credit settings and due date snapshot. Moving or removing a vehicle does not transfer old visits or debts. Historical individual visits can be associated explicitly with a reason, retaining original charges and all payments, subject to credit eligibility and Phase 8 closed-date protection. Visits already associated with a company cannot be transferred. Company association does not alter customer records.

Company charges use the visit creation business date (when the obligation is recorded); daily service reporting continues to use completion dates. Due dates use an explicit date, otherwise configured terms counted in calendar days from the charge date. Without either, due date remains NULL and debt is not classified as overdue. Overdue means outstanding with due_date before today's Ghana date. Unpaid cancellations remove the charge on the cancellation date in statements. Paid company visits cannot be cancelled without a future refund workflow. Charges and service breakdowns are protected once associated.

The only payment ledger remains payments plus payment_receipts. A company_payment_batches record groups receipt metadata and company_payment_allocations links each ordinary visit payment to the group. A receipt requires a positive GHS amount, a method/date, a reason and explicit positive per-visit amounts summing exactly to the total. No automatic FIFO rule, unallocated advance, negative balance or cross-company allocation is allowed. Duplicate keys return the original batch only for identical details. Main-process immediate transactions commit all allocations, receipts and audit logs together or roll everything back. Existing individual payments count exactly once and remain visible in company history. Allocated receipts and company financial associations are immutable.

Daily closing and dashboard collections read these ordinary visit receipts on their paid_at dates; company credit charges create no money receipt. Cash, Mobile Money, bank transfer, card and other remain separate. Phase 8 backdating restrictions and closing snapshot history remain intact. Dashboard company outstanding/overdue amounts are subsets of existing outstanding balances, never added to collections.

Account statements calculate opening balances from source charges and actual payments before the selected period, net charges and payments within the period, closing balances and outstanding visits as of the end date. They expose original visit IDs/numbers, receipt IDs and configured due dates. Print uses the system print dialog (PDF where offered); CSV download exports source amounts and identifiers with spreadsheet formula escaping. Documents are labelled account statements, with no invented invoice number or tax computation. Statements are recalculated from persisted records and are not formal immutable invoice documents.

Business rules to review: credit terms currently use calendar days from visit creation, and debts without due dates are not overdue; blank credit limit means uncapped authorized credit. Vehicle mappings apply to future visits, while visit assignments cannot be reassigned. Unallocated advances, paid-visit refunds, debt write-offs, company reassignment corrections, tax invoicing and persisted issued-statement versions remain outside this phase. Historical receipts dated before the original charge date require reconciliation before company association. Large company profiles currently load the full visit/payment history. Manual Electron checks of dialogs, printing and downloads remain to be performed.

Automated coverage includes registration, duplicate prevention, vehicle inheritance and history, credit limits/eligibility, partial/full/multi-visit receipts, duplicate submissions, overpayment, atomic rollback, overdue balances, period statements/cancellations, closing integrity, authentication, schema reinitialization and stale reviewed company assignments. Tests use isolated in-memory databases; no fictional records are inserted into the operational database.

Phase 10 — Financial Reports and Business Analytics

Reports and Analytics is an administrator-only, read-only module with Today, Yesterday, This week (Monday start), This month and Custom filters. Ghana uses UTC business dates. Presets stop at today's date; custom ranges are inclusive, cannot end in the future and are limited to 366 days. Date validation, money aggregation, pagination and CSV generation run in the Electron main process. SQLite read transactions give each summary/export a consistent source snapshot. New schema changes add reporting indexes only. Financial records, company allocations and closing snapshots are not modified.

Completed visit charges use stored visit totals and completion dates; legacy completions without a timestamp fall back to creation dates and are flagged. Service popularity and service/worker value use recorded line quantities and line values, which may differ from visit totals if visit-level adjustments exist. The report shows that difference rather than allocating it inventively. Category, service and worker names use stored snapshots. Actual completed receipts use payment dates, include company allocations through the ordinary payment ledger exactly once and remain separate from earned charges. Method reports describe collections, not earned revenue.

Outstanding balances, company balances, aging and worker payables are as of the selected end date and include history before the selected start. Outstanding visit balances include unfinished work created through that date. Payments after the end are excluded; known cancellation dates are honored. Undated historical cancellations make the exact historical balance unavailable; the report exposes a known subtotal and a notice. Customer/company labels use the currently preserved visit association snapshots, including any explicitly audited historical association. Overdue means a configured due date before the report end; no due date is not overdue. Aging uses days overdue in 1–30, 31–60, 61–90 and 91+ bands, with separate future/not-due and no-due groups. Credit utilization compares end-date balances with current limits; historical limit settings are not reconstructed.

Expenses are signed original events plus reversal events on their recorded business dates. A reversal subtracts once and originals remain visible for auditing. Cross-period reversals may produce a negative daily/category amount. Legacy expenses are included using stored amounts rounded to pesewas and flagged. Weekly/monthly totals contain only activity inside the selected period, including partial weeks/months.

Worker performance includes service quantities, stored categories, completed line value, confirmed earnings subtotal, actual recorded payouts and as-of payables. Unconfigured/review/missing compensation and salary services are counted as incomplete, not zero. Current salary agreements also prevent presenting complete compensation/payable totals; no salary accrual or payout is invented. Historical visit-level worker assignments without service allocation are flagged separately rather than apportioned among services. Confirmed payable subtotals subtract verified payouts through the end date; unresolved obligations and legacy payouts make the complete payable amount unknown. Actual legacy payout amounts remain visible but do not become verified service payouts.

Financial interpretation shows collections minus recorded paid expenses minus actual recorded payouts as a receipt/outflow difference. It is not net profit. Recorded cash movement is cash collections minus verified expense-event cash outflows and verified cash worker payouts; legacy outflows, opening cash, bankings and withdrawals are excluded. A permanent incomplete-data notice explains why net profit is unavailable: accrual expenses, salary obligations, tax, inventory and depreciation are not fully modeled. Reports require GHS business/visit records and refuse to invent exchange-rate conversions.

Daily closing reports read saved snapshot fields for opening cash, cash collections/outflows, expected/count cash and variances. Open days have NULL balances, not assumed zero. Reopened revisions remain visible. Only currently confirmed closings enter shortage/overage summary totals; reopened revisions are not summed twice. Legacy closings are labelled unverified and do not contribute to confirmed discrepancy totals. Closing status reflects the current revision, while historic cash amounts remain the original snapshot.

The renderer receives aggregated groups, at most 366 daily points and 50 detail rows per page. Offline SVG/HTML charts show daily charges versus receipts, popularity, expenses, payment methods and worker performance. Printing includes the loaded aggregates and the currently selected detail page with its row range clearly labelled. Full CSV exports use the selected dates and include every report section and detail table (up to 50,000 rows per section; larger exports fail clearly rather than silently truncating). CSV uses exact decimal GHS formatting, UTF-8, standard quoting and spreadsheet formula escaping while preserving signed numeric reversals.

Remaining limits: no formal profit figure, salary ledger, dated refund ledger, historical credit-limit reconstruction or frozen issued-report archive. Historical balances rely on currently persisted completed receipt statuses. Legacy amounts/date fallbacks need reconciliation for fully authoritative reporting. UI printing/download interactions still require manual Electron acceptance testing; large-database query performance should be evaluated against the deployed data size.

Tests cover date boundaries/presets, completed charges versus collections, partial/unpaid visits, end-date balances, expense reversals/aggregates, worker obligations/payouts/unknown compensation, company allocation/aging/utilization, closing snapshots/reopening, pagination, precise signed CSV, read-only preservation, safe monetary range and administrator authentication. Validation commands: npm.cmd run typecheck; npm.cmd run build; npm.cmd test.

Phase 11 — Business Settings, Administrator Security, Backup and Restore

Settings and Security is available from dashboard navigation to authenticated administrators. Business name, telephone, address and email update the existing business_settings row. Date presentation (long, day-first or ISO) and the page after sign-in (Overview, Visits or Reports) are stored as preferences linked to that business. Date presentation affects the dashboard and report displays; persisted business dates, filters, statement identifiers and CSV source dates stay in their canonical format. Existing tax settings are retained. The application version and database/default-backup locations are visible.

New logos are validated PNG/JPEG/WebP images up to 5 MB and stored in business_logo_assets inside SQLite. Real Electron uploads also pass native image decoding. Removing/replacing a logo is transactional and audited; legacy external files are retained rather than deleted. When an older external logo is used, backup converts that logo into an embedded asset in the backup copy only, leaving the operational database untouched. Missing/out-of-directory assets prevent an incomplete backup from being reported successful.

GHS is the only supported currency for new financial workflows. Existing currencies are preserved. A currency change to GHS is allowed only before prices, compensation rates, salary agreements or financial records exist; historical amounts are never relabelled or converted. Multi-currency conversion remains unsupported.

Administrator account editing updates the same user ID and requires the current password. New passwords retain bcrypt cost 12, the existing minimum-eight-character rule and the 72-UTF-8-byte limit. Username duplicates are rejected. Current-password failures share the application's failure counter and one-minute throttle after five failures. No password values or password hashes enter account audit details. Account updates revoke all sessions, including pending login attempts. No recovery password, hardcoded credential, second administrator or security-question workflow is created.

Manual backups use better-sqlite3's SQLite online backup API, not a filesystem copy of the live database. The administrator chooses a destination in a native directory dialog. Each successful backup is a uniquely named .wbbak folder containing database.sqlite and manifest.json. The copy is standalone (no WAL/SHM files), includes embedded logo data and all business/security records, and is validated before success is returned. Manifest metadata contains product ID, format/schema/application versions, creation date, database filename, SHA-256 checksum and logo-presence status; it contains no plaintext password or password hash. The database necessarily contains existing bcrypt password hashes. Backups are not encrypted: choose a private destination and protect the entire folder. POSIX restrictive modes are used where supported; Windows access follows destination-folder ACLs.

Verification checks SQLite file identification, checksum, integrity_check, foreign_key_check, registered business, active administrator/password-hash structure, exact installed application schema and compatible application major version. Application metadata identifies schema version 11 and backup format version 1. Unknown/custom schema objects, missing tables/constraints/triggers, corrupt/partial files, unexpected sidecars, linked backup files and incompatible versions are rejected. Raw SQLite files and pre-feature/custom backup formats are not automatically imported. Verification is read-only and does not touch operational data.

Restore sequence:
1. An administrator selects a backup folder through a native dialog. Verification runs first, then the verified database is staged privately beside the active file and checked again. The selection is bound to the current administrator/window/session and expires after five minutes. Logout/account changes discard prepared selections.
2. The administrator types RESTORE, supplies the current password and accepts a second native warning dialog. Cancel is the default in that dialog. The warning explicitly says current operational data will be replaced and restored accounts use passwords stored in the backup.
3. Database maintenance gates block other application database operations. A new online, validated safety backup of the current database is required first and retained under the application's backups directory.
4. SQLite is checkpointed and closed. Busy checkpoints or sidecars remaining from another live connection stop replacement. Files are not blindly overwritten or deleted. A durable restore journal records the original, staged and safety-backup locations; same-directory renames retain the original database as a .before-restore file and install the staged database.
5. The replacement is validated, reconnected with foreign keys and WAL enabled, and audited. A durable committed marker is written. Sessions are revoked and the UI returns to sign-in. This uses reconnection rather than requiring a full process restart.
6. On failure before commit, the original database is restored and reopened; rejected replacement files and safety backups are retained. On startup, a prepared journal recovers the original database while a committed journal preserves the verified restored database. Invalid recovery paths/journals fail closed instead of creating a blank database.

The application uses a single-instance lock. External SQLite tools must be closed before restore. Closing/quitting during maintenance is deferred until the operation settles. Successful backup/restore locations are recorded in backup-history.json outside the operational database so restoring an older database does not erase that history; the latest 100 operations are listed. Backup folders and previous-database recovery copies are not automatically deleted. History logging failures are reported separately and do not turn a verified copy into an unverified success claim.

Recovery guidance: keep the entire .wbbak safety folder, .before-restore database and any journal/failed-replacement files. Normal interrupted replacement recovery runs on startup. If automatic recovery reports that files are missing or a journal is invalid, stop using the application and obtain assistance; do not delete WAL/SHM files, reset the database or copy an active SQLite file. Once the application is recovered, use the authenticated restore UI to select a verified safety backup. Original operational data is retained in that safety backup and previous-database copy. Backups contain the credentials from their creation date; use those credentials after restore.

Limitations: no encryption/password recovery, scheduled/cloud backup, automatic retention deletion or legacy-format importer. Checksums detect corruption and change, not who authored a backup. Verification is deliberately strict to prevent restoring unexpected schema logic. File/directory durability ultimately depends on the operating system/filesystem; the recovery journal and retained copies provide process-crash recovery, not a guarantee against storage-device failure. Native dialogs and image decoding still require manual Electron acceptance checks. The live operational database was not restored during development; automated restore tests operate on isolated temporary databases.
